## 2. 세 가지 화면 목록의 관계

이 프로젝트에는 서로 다른 세 가지 '화면 목록'이 있고, 이들은 부분적으로만 겹친다.

1. [정의서] 요구사항정의서(Seq 1~36) + 기획정의서 — 반드시 구현해야 하는 화면/기능의 최종
   근거. 권한 계층(1계층 구매팀/2계층 기획팀/3계층 경영진) 단위로 조직됨. 여기 없는 화면은
   공식 구현 대상이 아니다(예: "ERP 영향 분석", "외부 리스크 모니터링"이라는 이름의 화면은
   Seq 표 어디에도 없음 — 2026-07-24 확인).

2. [데모(surin)] scratchpad/surin-check — 단일 관리자 패널 형태의 디자인/컴포넌트 참고용
   데모. 9개 최상위 nav 섹션, 22개 리프 중 5개만 실제 구현(대시보드/외부 리스크 모니터링/
   ERP 영향 분석/브리핑&의사결정지원/파일 업로드), 나머지는 Placeholder.tsx. **[정의서]와
   1:1 대응이 아니다** — surin에는 있지만 [정의서]엔 없는 화면(ERP 영향 분석 등)도 있고,
   반대로 [정의서]에 있는데 surin에 정확히 대응하는 화면이 없는 경우("리스크 현황판(상세)")
   도 있다. surin은 참고 자료일 뿐 구현 의무의 근거가 아니다.

3. [현재 구현] dev-김영진_merge-test — 실제 코드. [정의서]가 요구하는 것을 [데모(surin)]의
   시각적 구성을 참고해 이식하되, 권한 계층 구조에 맞게 재배치한다. 예: surin '대시보드'
   화면 요소 대부분이 PurchasingDashboardPage(1계층 구매팀 대시보드) 안에 섹션으로 흡수됨.

원칙: "무엇을 만들지" 결정은 항상 [정의서]가 최우선 근거이고, [데모(surin)]는 "어떻게
만들지"의 시각/컴포넌트 참고 자료일 뿐 구현 여부의 근거가 아니다. 두 목록의 이름이 같아도
(예: "브리핑") 개념이 다를 수 있으므로(2026-07-24 C3에서 발견: surin "브리핑&의사결정지원"은
이벤트 비종속 종합 브리핑, 우리 BriefingDetailPage는 riskEventId 필수 개별 이벤트 브리핑 —
서로 다른 개념) 매번 실제 코드/문서 원문을 대조해야 한다.
